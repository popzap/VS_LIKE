## 1. 🔴 1순위 — **그림이 없어서 게임이 헷갈린다**

여기 둘은 취향이 아니라 **판독성 문제**다. 다른 무엇보다 먼저다.

### 1-1. 🔴 내 총알과 적 총알이 **같은 그림**이다

```
Proj_Bullet    -> Assets/Game/ICON/Bullet.png
Proj_EnemyBolt -> Assets/Game/ICON/Bullet.png   ← 같다
```

색만 다르다(적탄은 붉은 틴트 + 0.55 스케일). **탄막 게임에서 내 탄과 적 탄이 같은 모양이면
피할지 쏠지를 순간적으로 못 가른다.** 특히 `Gun` 직업은 화면에 자기 탄을 계속 깔아 둔다.

| | 지금 | 필요 |
|---|---|---|
| 플레이어 탄 | 노란 원 50px | **길쭉한 탄** — 진행 방향이 보이는 모양 |
| 적 탄 | 같은 원, 붉은 틴트 | **다른 실루엣** — 둥글고 가시 있는 형태 등 |

> 🔑 **색으로만 가르면 안 되는 이유** — 이 게임은 엘리트/보스를 **외곽선 색**으로 표시하고
> (보라·빨강, `C21`) 피격 플래시도 색이다. 화면에 색 신호가 이미 셋이라 넷째를 색으로 얹으면 안 읽힌다.
> **모양으로 갈라야 한다.**

### 1-2. 🔴 `Bullet.png` 만 **50×50** 이다

다른 스프라이트는 전부 256~1536 인데 이것 하나만 50px 다. 확대되면 뭉갠 자국이 그대로 보인다.
`ICON/` 폴더에 있는 것부터가 **아이콘을 투사체로 가져다 쓴 흔적**이다
(같은 폴더의 `goblin.png`·`Exp_Orb.gif` 도 지금 아무 데도 안 쓰인다 — 정리 대상).

## 2. 🔴 2순위 — **UI 가 통째로 단색 사각형이다**

기능은 전부 돌아간다. **화면이 프로토타입처럼 보인다는 것**이 문제다.
포트폴리오 제출물이 **시각화 중심 PDF** 라는 걸 생각하면 여기가 가장 크게 남는다.

| 화면 | 지금 | 필요한 그림 |
|---|---|---|
| **메인 메뉴** | 단색 판 + 글자 | 배경 1장 · 로고/타이틀 · 버튼 프레임 |
| **상점** | 단색 카드 3장 | 🔴 **상점 주인 1장** · 카드 프레임 · 가격표 배지 |
| **레벨업 카드** | 단색 카드 | 카드 프레임(등급별 테두리) |
| **메타 강화** | 단색 카드 7장 | 🟡 강화 아이콘 7장(`Icon` 열이 **비어 있다**) · 카드 프레임 |
| **스테이지 맵** | 단색 노드 | 노드 아이콘 5종(전투·엘리트·상점·이벤트·보스) · 연결선 |
| **HUD** | 바 + 글자 | 🟡 **초상 표정 4장**(슬롯이 코드에 있고 `fileID: 0` 이다) · 프레임 |
| 일시정지 · 옵션 · 결과 | 단색 판 | 공용 패널 프레임(9-slice) 하나면 다 덮는다 |

> 🔑 **공용 프레임 하나가 화면 여섯을 바꾼다.** 패널·카드·버튼은 전부 같은 사각형이라
> **9-slice 프레임 3종**(패널 / 카드 / 버튼)만 만들면 UI 전체가 한 번에 올라간다.
> 개별 화면을 하나씩 그리는 것보다 **압도적으로 싸다.** 여기부터다.

### 🟡 메타 강화 아이콘 7장 — 이미 자리가 있다

`Upgrades.csv` 의 `Icon` 열이 **7행 다 비어 있다.** `UpgradeCardUI` 가 아이콘이 없으면
`Image` 를 꺼 주도록 돼 있어 **안 깨지지만 글자만 나온다.**
경로만 채우면 되므로 **배선 비용이 0** 이다 (Import 1회).

대상: Vitality(`MaxHp`) · Power(`Damage`) · Magnetism(`PickupRadius`) ·
Insight(`XpGain`) · Precision(`CritMultiplier`) · Toughness(`Armor`) · Swiftness(`MoveSpeed`)

⇒ **패시브 아이콘 11장이 이미 있다.** 같은 스탯이 6개 겹치므로(`MaxHp`·`Damage`·`PickupRadius`·
`XpGain`·`Armor`·`MoveSpeed`) **재사용하면 6장은 공짜**고 새로 만들 건 `CritMultiplier` **1장**뿐이다.

## 6-1. ✅ 1·2번 만들었다 (`C33`, 2026-09-04) — 두 번 다시 그렸다

| 파일 | 규격 |
|---|---|
| `Sprites/Projectiles/PlayerBullet.png` · `EnemyBolt.png` | 256² · **PPU 512** · Point · 색 5개 |
| `Sprites/UI/UI_Panel.png` (128²) · `UI_Card.png` (96²) · `UI_Button.png` (64²) | PPU 100 · Bilinear · 🔴 `spriteBorder` **40 / 28 / 20** |

생성기: `Tools/Art/gen_projectiles.py` · `Tools/Art/gen_ui_frames.py` (수치를 바꾸려면 여기 상단만 고친다)

**두 번 틀렸고 둘 다 눈으로 잡았다** — 여기 남겨 둘 값이 있다:

1. **좌우 대칭이면 방향이 사라진다.** 예광탄의 최대 두께를 가운데(0.62)에 뒀더니
   렌즈 모양이 되어 어느 쪽으로 가는지가 안 보였다. 정점을 코 쪽(0.80)으로 밀어야
   혜성 꼬리가 되고 그제서야 방향이 읽힌다
2. 🔴 **"예쁘게"가 아니라 "옆 물건과 같은 재질로"가 기준이다.** 처음에 매끈한
   그라디언트 글로우로 뽑았는데 `Arrow.png` 옆에 놓으니 **혼자 다른 게임 물건**이었다.
   `Arrow`·`Shuriken` 을 실측하니 **256px 안에 4px 블록 = 논리 64×64**, 색 7~13개, 검은 외곽선이었다.
   그 격자에 맞춰 다시 그렸다

> 🔑 **새 그림을 넣기 전에 옆에 놓일 그림을 먼저 잰다.** 이 프로젝트는 규격이 문서가 아니라
> **기존 파일에** 있다 (직업 걷기 시트 PPU 256 도 그렇게 나왔다 — `C28`).

#### 🟡 정정 — 탄환은 "크기 무변화"가 아니라 **+22 %** 였다 (`D40` 지적 · `C36` 확인)

*"`50px ÷ PPU 100 = 0.5 유닛`이라 기존과 같다"* 고 적었는데 **파일 크기와 스프라이트 rect 를 혼동했다.**
파일은 50×50 이지만 `Bullet.png` 의 **스프라이트 rect 는 41×41** 이다(여백이 트리밍돼 있었다).

```
옛것  41px ÷ PPU 100 = 0.41 유닛
새것 256px ÷ PPU 512 = 0.50 유닛     → +22 %
```

🔑 **그런데 결론은 맞았다 — 이유가 다르다.** 크기가 같아서가 아니라 **명중 판정이 스프라이트와 무관**해서다:
플레이어 탄은 프리팹의 `CircleCollider2D radius 0.5`, 적탄은 `EnemyProjectile.cs:14` 의
`HitRadius = 0.45f` **상수**다(주석에도 *"스프라이트 크기와 무관한 고정값"* 이라고 적혀 있다).

⇒ **오히려 나아졌다.** 예전엔 0.41 유닛짜리 그림이 반경 0.5 짜리 판정을 갖고 있어
**보이는 것보다 넓게 맞았다.** 지금은 그림과 판정이 거의 같다.

#### 🔴 9-slice 를 넘길 땐 **"어디에 쓸지"를 같이 줘야 한다**

`spriteBorder`(40/28/20)만 주고 **대상 크기를 안 줬다.** `D40` 이 배선하다 막혔다 —
`ShopRemoveRow/RemoveButton` 이 **38×38** 인데 테두리가 위아래 **20+20 = 40px** 이라
**버튼보다 테두리가 크다.**

`D40` 이 정한 규칙이 옳고, 여기 남긴다:

> **테두리 총합이 짧은 변의 60 % 를 넘으면 `Image.pixelsPerUnitMultiplier` 로 그만큼 줄인다.**

| 대상 | 크기 | 배율 | 화면 테두리 |
|---|---|---|---|
| `ItemCard/SelectButton` | 130×30 | 2.2 | 9px |
| `ShopRemoveRow/RemoveButton` | 38×38 | 1.8 | 11px |
| `UpgradeCard/BuyButton` | 210×48 | 1.4 | 14px |
| `PausePanel/*Button` | 300×60 | 1.1 | 18px |
| 340×78 이상 | — | 1.0 | 20px 그대로 |

🔑 **텍스처 규격은 "무엇을 만들었나"고, 9-slice 는 "어디에 얹히나"까지가 규격이다.**
다음에 프레임을 만들면 **가장 작은 대상의 짧은 변**을 같이 재서 넘긴다.

**UI 프레임의 색 배분** — 명암을 알파가 아니라 **RGB** 로 줬다
(테두리 1.00 / 홈 0.42 / 안쪽 하이라이트 0.72 / 채움 0.30).
`Image.color` 는 텍스처에 **곱해지므로**, 알파로만 주면 어두운 색으로 칠했을 때 테두리와 안쪽이
구분되지 않는다. RGB 로 주면 **어떤 색으로 칠하든 밝은 테두리 + 어두운 판**이 유지된다.
⇒ DEV 는 기존 `Image.color` 를 **그대로 두고** `Source Image` 만 꽂으면 된다.

## 8. 🔴 새 직업 그림을 만들 때 — `ArtFacesRight` 를 같이 정한다 *(C51 · `D100` 요청-60)*

걷기 시트가 전부 **정면 그림**이라 *"향하는 쪽"* 이 없다. `flipX` 는 좌우를 통째로 뒤집을
뿐이라 **무기를 어느 손에 그렸는지**가 곧 기본 방향이고, 그게 **직업마다 엇갈린다.**
⇒ `Classes.csv` 의 **`ArtFacesRight`**(19번째 열)가 그 값을 들고 있다.

| 값 | 뜻 | 현재 |
|:---:|---|---|
| `1` | 무기가 **그림 오른쪽** | Ranger(활) · Sentinel(총구) · Aegis(총구) |
| `0` | 무기가 **그림 왼쪽** | Warrior(칼) · Warden · Mage · Doomlord · Demolitionist · Assassin · Summoner |

### 🔴 자동으로 판정하지 말 것 — **두 세션이 각각 다른 지표로 실패했다**

| 누가 | 무엇을 쟀나 | 결과 |
|---|---|---|
| `D100` | 불투명 픽셀 **무게중심** | Ranger 가 `-0.58 %` 로 *"중앙"* — 활은 확실히 오른쪽인데 |
| `C51` | 몸통 밖 **얇은 꼬리 길이** | 10종 중 **8종 적중**, 그런데 **Warrior 를 틀렸다** |

🔑 **둘 다 "무기" 를 안 쟀다.** 무게중심은 **몸통 질량**을, 꼬리는 **아무 돌출물**을 쟀다 —
Warrior 의 오른쪽 꼬리 13.9 는 칼이 아니라 **망토와 어깨**였다.
🔴 **그리고 하필 사용자가 직접 지적한 그 한 종을 틀렸다.** 8/10 은 위험한 성적이다 —
**맞은 8개가 틀린 2개를 가려 준다.**

⇒ **그림을 연다.** 프레임 하나를 **마젠타 배경에 얹어** 보면(투명 경계까지 보인다) 1초다.

```python
from PIL import Image
im = Image.open("Assets/Game/Sprites/Classes/Walk/<Class>_Walk.png").convert("RGBA")
bg = Image.new("RGBA", (256, 256), (255, 0, 255, 255))   # 대조 배경
bg.alpha_composite(im.crop((0, 0, 256, 256)))
bg.convert("RGB").resize((384, 384), Image.NEAREST).save("out.png")
```

### 🟡 무기가 둘이면 — **승급 사슬을 본다**

`Warden` 은 **방패 왼쪽 · 칼 오른쪽**이라 규칙이 한 답을 안 준다.
그럴 땐 그림이 아니라 **승급으로 정한다** — `Warrior`(`0`) → `Warden` 은 **한 판 안에서**
갈아 끼우므로, 값이 다르면 **승급하는 순간 캐릭터가 좌우로 뒤집힌다.**
⇒ **사슬 안에서는 값을 유지한다.** (`Warden = 0`)

🟡 **근본 해법은 그림을 통일하는 것**(전 직업 무기를 오른쪽으로)이고 그러면 이 열이 통째로
필요 없어진다. 다만 **10종 중 7종을 다시 그려야 하고 사용자가 이미 본 그림들**이라
마감(2026-09-07) 뒤에 판단한다.
