# D19 — 펫이 꼬리처럼 따라온다 (기차)

**세션:** DEV · **날짜:** 2026-08-31
**지시:** 사용자 (2026-08-31)

> 펫류 무기 들이 플레이어에서 고정된 위치에서 움직이게 설정되 있는거 같은데
> 나는 꼬리처럼 따라오는 방식을 생각하고 있어
> 펫류 무기가 많아지면 기차처럼 늘어지게

---

## 왜 했나

소환수는 **플레이어 둘레를 공전**하고 있었다. `SummonWeapon.FollowTarget()` 이
프리팹에 박힌 `offsetAngle` 로 방향을, `offsetDistance` 로 거리를 잡아
**플레이어 기준 고정 좌표**를 목표로 삼았다.

```cs
float rad = offsetAngle * Mathf.Deg2Rad;
return p + new Vector2(Mathf.Cos(rad), Mathf.Sin(rad)) * offsetDistance;
```

문제가 둘이다.

| # | 무엇 | 왜 |
|---|---|---|
| ① | 플레이어가 꺾으면 소환수가 **옆으로 미끄러진다** | 목표점이 플레이어와 같이 통째로 회전한다. "따라온다"가 아니라 "매달려 있다" |
| ② | 각도를 **손으로 배분**해야 겹치지 않는다 | 드래곤 90° · 문어 210°. 소환사는 무기 칸이 5개라 셋째부터 답이 없다 |

### 🔴 곁가지로 확인한 것 — 문서가 틀렸다

[`TUNING.md` §3](../../TUNING.md) 의 "소환수가 서는 자리" 는
**"3마리 이상이면 72° 간격으로 재배치된다"** 고 적고 있고,
CONTENT 도 [`REQ/DEV.md` 요청-16](../REQ/DEV.md) §3 에서 그걸 근거로 각도 조정을 보류했다.

**그런 코드는 없다.** `offsetAngle` 은 전 프로젝트에서 **딱 한 곳**에서만 읽힌다:

```
Assets/Scripts/Weapon/SummonWeapon.cs:104   float rad = offsetAngle * Mathf.Deg2Rad;
```

재배치도, 개수 세기도 없다. 5마리를 들면 **프리팹 값 그대로 겹쳐 선다.**
→ CONTENT 에 회신([`REQ/CONTENT.md`](../REQ/CONTENT.md) 요청-13)에서 정정을 요청했다.

## 무엇을 했나

**"플레이어 기준 오프셋"을 버리고 "플레이어가 지나온 길"을 따라간다.**

| 경로 | 무엇 |
|---|---|
| `Assets/Scripts/Player/PlayerTrail.cs` | **신설.** 플레이어가 지나온 길을 짧게 기억하고, 길 위 임의 거리의 점을 돌려준다 |
| `Assets/Scripts/Weapon/SummonWeapon.cs` | 공전 → **기차**. 정적 줄(`Train`)에 등록하고 길 위 자기 칸 자리를 따라간다 |

### ① 길 기억 — `PlayerTrail`

- 플레이어가 `minStep`(0.08유닛) 움직일 때마다 자국을 하나 남긴다
- 총 `maxLength`(14유닛)까지만 들고 뒤부터 버린다
- `SampleBack(d)` = 지금 자리에서 **길을 따라** `d` 유닛 거슬러 올라간 점
  — 직선 거리가 아니라 **길 위의 거리**다. 그래서 꺾인 자리를 지나간다

### ② 줄 세우기 — `SummonWeapon.Train`

```cs
private static readonly List<SummonWeapon> Train = new();
```

**얻은 순서가 곧 칸 순서다.** 내 뒤처짐 거리 = **앞칸들의 `offsetDistance` 누적 합**.
곱셈이 아니라 합이라 칸마다 간격을 다르게 줄 수 있다.

```
1번칸(드래곤) 1.2  ─  2번칸(문어) 1.2+1.2 = 2.4  ─  3번칸 3.6 …
```

⇒ **소환수를 더 모을수록 줄이 그대로 뒤로 길어진다.** 이게 "기차처럼 늘어지게"다.

### 왜 세 가지를 굳이 이렇게 했나

| 결정 | 이유 |
|---|---|
| **씬에 배선하지 않는다** (`PlayerTrail.Of` 가 없으면 붙인다) | 소환수는 무기 획득 시점에 생긴다. 그때 배선이 돼 있으리란 보장이 없고, 요구하면 `SceneWiring.csv`(**CONTENT 소유**)까지 건드려야 한다 |
| **`SampleBack` 이 스스로 기록한다** (프레임 번호로 잠금) | `PlayerTrail.LateUpdate` 와 `SummonWeapon.LateUpdate` 의 **실행 순서가 보장되지 않는다.** 어느 쪽이 먼저 와도 한 프레임에 딱 한 번만 기록된다 |
| **런 시작에 길을 미리 깔아 둔다**(`Seed`) | 빈 채로 두면 런이 시작하는 순간 **소환수가 전부 발밑에 겹쳐 있다가** 움직여야 풀린다 |
| **3유닛 넘게 순간이동하면 길을 지운다** | 런 재시작·스테이지 이동에서 플레이어가 통째로 옮겨진다. 옛 길을 두면 소환수가 **화면 밖 옛 자리까지 줄을 서서** 끌려간다 |

### `offsetAngle` 은 남겨 뒀다

지웠다가 프리팹 직렬화 값이 어긋나는 게 싫어서가 아니라, **`OwnerStats` 가 없을 때의
물러날 길**이 필요하다. 평소에는 안 쓰인다 — 툴팁에 그렇게 적었다.

## 어떻게 확인했나

임시 프로브(`__D19TrailProbe`)로 **플레이어를 ㄱ자로 몰았다** — +X 로 3초, 직각으로 꺾어 +Y.
드래곤·문어를 실제 지급 경로(`LevelUpManager`)로 주고 매 구간 위치를 찍었다.

🔑 **대조군을 같은 줄에 찍었다** — "옛 방식(고정 각도)이었다면 어디 있었을까"와의 거리.

### ① 런 시작 직후 (아직 안 움직였다)

```
플레이어=(3.71,1.08)  Dragon 상대=(-1.20,+0.00) 거리=1.20
                      Octopus 상대=(-2.40,+0.00) 거리=2.40
```

**1.20 / 2.40 — 누적 합 그대로다.** 발밑에 뭉치지 않는다(`Seed` 가 듣는다).

### ② 직선 주행 중

```
Dragon 상대=(-1.87,+0.00)   Octopus 상대=(-3.07,+0.00)
```

칸 간격 `3.07 - 1.87 = 1.20` **일정**. 플레이어와의 거리만 1.20 → 1.87 로 벌어지는데
이건 `followLerp` 감쇠의 정상상태 지연이고 **계산과 맞는다**:

```
지연 = 속도 / followLerp = 4 / 6 = 0.667
1.20 + 0.667 = 1.867   <- 실측 1.87
```

### ③ 🔑 직각으로 꺾는 순간 — 여기가 핵심

| t | 플레이어 | Dragon 상대 | 꺾인점까지 | Octopus 상대 | 꺾인점까지 |
|---|---|---|---:|---|---:|
| 0.25 | (15.71, 2.07) | (-0.90, -0.99) | **0.90** | (-2.10, -0.99) | **2.10** |
| 0.50 | (15.71, 3.07) | (-0.21, -1.67) | **0.39** | (-1.11, -1.99) | **1.11** |
| 1.00 | (15.71, 7.27) | (+0.00, -1.87) | 4.31 | (+0.00, -3.07) | 3.11 |

- t=0.25 — 플레이어는 이미 위로 1유닛 갔는데 **둘 다 아직 수평 구간 위**(`y` 상대 -0.99)
- t=0.50 — **드래곤이 먼저 모퉁이를 돈다**(0.39). 문어는 아직 1.11 밖 → **차례로 돈다**
- t=1.00 — 둘 다 수직 구간에 정렬. `x` 편차 **0.00**

### 판정

| # | 확인할 것 | 결과 |
|---|---|---|
| ① | 시작부터 늘어서 있다 (발밑에 안 뭉친다) | ✅ 1.20 / 2.40 |
| ② | 칸 간격이 일정하다 | ✅ 항상 **1.20** (정지·주행·회전 전부) |
| ③ | 🔑 **길을 되짚는다** — 꺾을 때 옆으로 안 미끄러진다 | ✅ 꺾은 뒤 `x` 편차 **0.00** |
| ④ | 🔑 **앞칸이 먼저 돈다** (기차/뱀 거동) | ✅ t=0.50 에 드래곤 0.39 · 문어 1.11 |
| ⑤ | 옛 방식과 실제로 다르다 (대조군) | ✅ 옛자리와의 차 **1.13 ~ 3.08** — 한 번도 안 겹친다 |
| ⑥ | 컴파일 에러 0 · 콘솔 경고/에러 0 | ✅ 0건 |

**정리 확인** — 임시 스크립트 `__D19TrailProbe.cs` **삭제 완료**(`Assets/Scripts/__D19*` 없음) ·

## 알게 된 것

### 대조군을 **같은 로그 줄에** 찍으면 판정이 안 흔들린다

"소환수가 (-0.90, -0.99) 에 있다"만으로는 맞는지 알 수 없다. 옆에
**"옛 방식이었다면 여기서 2.37 떨어진 곳"**을 같이 찍으니 한 줄로 끝났다.
D17 의 렌더 픽셀 실측, D18 의 두 장부 뺄셈과 같은 수법이다 —
**값을 찍지 말고 차이를 찍는다.**

### 문서가 코드 동작을 주장하면 의심한다

`TUNING.md` 의 "72° 재배치"는 **아무도 짜지 않은 기능**인데 두 세션이 그걸 근거로
판단을 미루고 있었다. 확인은 `grep` 한 번이었다(`offsetAngle` 사용처 1곳).

### 이 변경이 요청-16(촉수가 플레이어를 덮는다)에 영향을 준다

문어가 **2번칸**이면 플레이어에게서 정지 **2.40** · 주행 **3.07** 뒤에 선다.
`Range` 는 Lv1 1.8 ~ Lv5 2.6 이므로 —

| 상황 | 문어 거리 | Lv5 `Range` 2.6 | 덮나 |
|---|---:|---:|---|
| 예전(공전) | 1.20 | 2.6 | 🔴 **항상 덮는다** |
| 지금 · 2번칸 · 정지 | 2.40 | 2.6 | 0.2 만 걸친다 |
| 지금 · 2번칸 · 주행 | 3.07 | 2.6 | ✅ **안 덮는다** |
| 지금 · **문어만** (1번칸) | 1.20 | 2.6 | 🔴 여전히 덮는다 |

⇒ **요청-16 의 `m_SortingOrder 20 → -5` 는 여전히 해야 한다** (문어 단독일 때가 남는다).
다만 대가로 잃는 "촉수 자기 잉크 3.7~4.2%" 는 **줄이 길수록 줄어든다.**
