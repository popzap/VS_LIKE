## 왜 했나

D10 이 **관통·근접**으로 무기의 *공격 방식*을 갈랐다면, 3·4단계는 **시간축**을 연다.

- **바닥 폭탄** — 지금 모든 폭발은 *닿는 즉시* 터진다. **기다렸다 터지는 것**이 하나도 없어서
  "저기 폭탄이 떨어졌으니 피해야겠다"는 판단이 게임에 존재하지 않았다
- **독 장판** — 이 게임에 **지속 피해(DoT)도 슬로우도 개념 자체가 없었다.**
  적을 느리게 만드는 수단이 전무해서, 몰려오면 무조건 도망만 답이었다

## 무엇을 했나

### ① `BombProjectile` 에 신관 (기존 파일 수정 1/2)

```csharp
[SerializeField] private float    fuseTime   = 0f;   // 0 = 지금까지의 동작(곡사포)
[SerializeField] private Sprite[] fuseFrames;        // 비면 그림 안 바뀜
```

착탄 후 `fuseTime` 을 세고 터진다. 그동안 `fuseFrames` 를 **시간 게이지**로 훑는다 —
루프 애니메이션이 아니라 `_fuseElapsed / fuseTime` 로 인덱스를 찍는다. 0=차가움, 마지막=벌겋게.

**걸림돌 둘.**

**(가) 바닥에 놓인 폭탄이 팽이처럼 돈다.** 비행 중 `spinSpeed 540°/s` 로 자전하는데
착탄해도 계속 돌면 신관 그림이 빙빙 돈다. 착탄 시 `transform.rotation = Quaternion.identity` 로 굳힌다.

**(나) 풀 재사용.** `_fusing` · `_fuseElapsed` · 첫 프레임을 `Initialize()` 에서 되돌린다.
안 그러면 두 번째로 꺼낸 폭탄이 **이미 다 탄 신관**을 들고 나온다.

🔴 **곡사포는 안 건드렸다.** `fuseTime = 0f` 는 C# 초기값이라 기존
`Proj_Bomb.prefab` 에 **직렬화되어 있지 않다.** 미직렬화 필드는 초기값이 먹으므로
프리팹 파일이 그대로여도 `fuseTime == 0` → 예전처럼 즉폭. D10 의 `pierceCount = 1` 과 같은 수법이다.
그래도 믿지 않고 **대조군 회귀 검사**를 돌렸다(판정 ②).

### ② `EnemyBase` 에 슬로우 (기존 파일 수정 2/2)

```csharp
private float _slowMult = 1f;   // 1 = 슬로우 없음
private float _slowUntil;       // 이 시각을 넘기면 저절로 풀린다
protected float CurrentSpeed => MoveSpeed * (Time.time <= _slowUntil ? _slowMult : 1f);
```

🔴 **`MoveSpeed` 를 덮어쓰지 않는다.** 원본은 손대지 않고 **읽는 쪽에서 곱한다.**
덮어썼다면 슬로우를 푸는 코드가 "원래 값"을 어딘가에 따로 보관해야 하고,
그 보관값이 풀 재사용을 건너뛰면 적이 영구히 느려진다.

**Enter/Exit 을 짝맞추지 않는다.** 장판이 **매 틱 짧게 다시 걸고**, 안 걸어 주면 만료된다.
Trigger 방식이면 적이 장판 안에서 **죽거나 풀로 반납될 때 Exit 가 안 와서**
슬로우가 붙은 채로 재사용된다 — 이 게임은 적이 풀에서 도는 게 정상 경로라 확실히 터진다.

**겹침은 "가장 센 것 하나만".**

```csharp
if (Time.time > _slowUntil || mult < _slowMult) _slowMult = mult;
_slowUntil = Mathf.Max(_slowUntil, Time.time + duration);
```

곱했다면 장판 2개가 겹칠 때 `0.6 × 0.6 = 0.36` — 적이 사실상 **멈춘다.**
장판을 여러 개 까는 게 이 무기의 성장 방향이라 반드시 터졌을 함정이다(판정 ⑥).

**풀 재사용 초기화는 `Setup()` 이 아니라 `Initialize()` 다.** 요청서가 메서드 이름을
잘못 짚었다 — 실제 재사용 리셋 블록(`_knockbackTimer`, 사망 팝 코루틴, 콜라이더)은
`Initialize()` 안에 있다. 거기에 `_slowMult = 1f; _slowUntil = 0f;` 를 넣었다.

이동 3곳(추적 · 배회 · 돌진)을 `CurrentSpeed` 로 바꿨다.
`Visual.Setup(sr, MoveSpeed, ...)` 는 **일부러 `MoveSpeed` 그대로** 뒀다 —
걷기 애니메이션의 기준 속도라, 느려질 때마다 프레임레이트까지 흔들 이유가 없다.

### ⑤ 🔴 요청서의 장판 규격 2개가 그림과 달랐다 — 실측으로 고쳤다 (사용자 승인)

요청서는 **"Pivot Center"** 와 **"`spriteRadiusAtScaleOne = 1.0` 고치지 말 것"** 을 못 박았다.
코드를 쓰기 **전에** 셀의 알파를 재 봤더니 **둘 다 틀렸다.**

```
그려진 원   중심 (134, 132)px · 반지름 ≈ 97px      (셀 256px, 중앙은 128,128)
→ pivot      x = 134/256 = 0.5234375
             y = (256-132)/256 = 0.484375          (PIL 은 위에서, Unity 는 아래에서 잰다)
→ 반경       97 / 100(PPU) = 0.97 유닛
```

**중심이 6px 오른쪽, 4px 위로 치우쳐 있다.** Center 피벗을 쓰면 **맞는 원과 보이는 원이 어긋난다.**
`1.0` 을 쓰면 그림이 3% 작게 나온다 — 요청서 계약 "그림 반지름 = 맞는 반지름" 의 위반이다.

**사용자에게 물어 `실측값으로 보정` 을 택했다.** D10 의 `1.074` 와 똑같은 나눗셈 패턴:

```csharp
transform.localScale = Vector3.one * (radius / spriteRadiusAtScaleOne);   // 0.97
```

보정이 실제로 먹었다는 증거는 판정 ⑧에 있다 — 화면상 중심 오차가 **0.7px** 다.
피벗 보정이 없었다면 x 로만 약 **6.7px** 어긋났어야 한다(6 스프라이트px × 스케일 1.237 × 0.9).
**10배 차이다.**

### 판정-③ — 슬로우가 남의 속도를 갉아먹지 않았나

`EnemyBase` 는 **모든 적의 부모**다. 이동 3곳을 건드렸으니 조용히 망가질 수 있었다.

```
[D11] REUSE   normal=2.200  slowed=0.660(0.300x)  reinit=2.200(1.000x)
[D11] SPEED-BEFORE  avg=1.493  max=6.000
[D11] SPEED-AFTER   avg=1.885  max=6.000
```

- `0.300x` — 건 배율 그대로다. 오차 0
- `reinit=1.000x` — 30초짜리 슬로우가 걸린 채 `Initialize()` 를 다시 부르자 **즉시 원속**.
  이게 곧 풀에서 다시 꺼내는 경로다. 리셋이 `Setup()` 이 아니라 여기 있어야 하는 이유
- `SPEED-BEFORE/AFTER` — 장판을 다 쓰고 난 뒤 **max 가 6.000 으로 동일**하다.
  (avg 가 오른 건 시간이 지나 빠른 적 비율이 늘어서다. max 가 안 변한 게 회귀 없음의 증거다)

### 판정-④ — 폭탄이 "달아오른다"를 어떻게 쟀나

`BOMB-GROUND flight=0.53s fuseTotal=1.10s` — 비행 시간은 `PLAIN` 과 **완전히 같고**,
착탄 뒤 `1.10s` 가 더 붙었다. 프레임은 fuse `0.00 / 0.28 / 0.55 / 0.83` 에 정확히 4등분.

**`rotZ` 는 착탄 후 모든 로그에서 `0.0`** 이다 (첫 줄만 `284.2` — 이건 프로브 아티팩트다.
프로브의 착탄 판정 허용치가 `sqrMagnitude < 0.0004`(=0.02유닛)라 **실제 착탄 한 프레임 전**에
먼저 찍힌다. 그 다음 프레임부터 전부 0).

### 판정-⑥ — 0.36 이 나왔는지 어떻게 갈랐나

장판 2개를 **같은 자리에 겹쳐** 깔고 안쪽 적의 속도를 훑었다.
관측된 감속 속도는 **오직 두 값**뿐이다:

```
0.840 = 1.400 × 0.6      (느린 적)
1.320 = 2.200 × 0.6      (빠른 적)
```

곱셈 누적이었다면 `1.400 × 0.36 = 0.504` · `2.200 × 0.36 = 0.792` 가 섞여 나왔어야 한다.
**한 번도 안 나왔다.** "가장 센 것 하나만" 이 실제로 동작한다.

### 판정-⑧ — 봤다, 그리고 쟀다

`Unity_Camera_Capture(cameraInstanceID: -1602)` 로 **게임 카메라**를 찍었다
(인자 없이 부르면 씬 뷰가 찍힌다). ortho 6 · 1920×1080 → **90 px/유닛**.

**눈으로 확인한 것:** 초록 장판이 플레이어·적 **아래**에 깔리고,
그 위에서 피해 숫자(4·10·5·10)가 **틱마다** 떠오른다. 안팎의 적이 모두 보인다.

**픽셀로 쟀다:**

```
scale        = 1.237                  (= 1.2 / 0.97)
렌더러 bounds = (3.17, 3.17)           (= 2.56 × 1.237)
기대 중심     = (935.7, 520.6)  기대 반지름 = 108.0px
실측 중심     = (935.0, 520.0)        →  🔴 오차 0.7px
실측 반지름   = 코어 rx 104.5 / ry 102.5  ·  알파 끝 rx 109.1 / ry 106.9
```

**기대 반지름 108.0 이 "진한 초록 코어"와 "알파가 끝나는 지점" 사이에 정확히 들어간다.**
가장자리가 흐리게 페이드되는 그림이라 이게 맞는 결과다.

## 같이 나온 것

**프로브의 위치 허용치가 한 프레임 일찍 터졌다.** 허용치 `0.02유닛` 이 프레임당 이동거리보다
작지 않으면 "도착"이 실제보다 먼저 잡힌다. 판정 ④의 `rotZ=284.2` 유령의 정체다.
**증상을 코드 버그로 착각하기 딱 좋았다.**

**레벨업 패널이 측정을 통째로 멈춘다.** `timeScale = 0` 이라 프로브 코루틴이 정지한다.
`WaitForSecondsRealtime` 으로 도는 감시 코루틴을 붙여 `LevelUpManager.HidePanel()` 로 닫았다.
**긴 런타임 측정을 하려면 이게 필수다.**

**바닥은 `SpriteRenderer` 가 아니라 Tilemap 이다.** 픽셀 측정용으로 화면을 비우려고
모든 `SpriteRenderer` 를 껐는데 배경이 그대로 남아, 밝기 임계값이 화면 전체(2,073,600px)를
잡았다. 초록 마스크 방식으로 우회했다.

**`result.Log` 는 서식 지정자를 안 먹는다.** `{0}` 만 치환한다 — `{6:F1}` 은 글자 그대로 찍힌다.
`.ToString("F1")` 로 문자열을 이어 붙일 것.

**`RunCommand` 는 `System.Reflection` 을 통째로 거부한다.** `BindingFlags` 한 단어만 있어도 스크립트 전체가 반려된다.
