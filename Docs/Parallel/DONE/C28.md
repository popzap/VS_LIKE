## 3. 🔴 ③ 의 답 — **수명 상한을 두지 않는다**

물어본 축(수명)으로는 **거래가 성립을 안 한다.**

| | | 근거 |
|---|---|---|
| 얻는 것 | **0.5 ms/frame** = 60 fps 예산의 **3 %** | `PERF.md` §8-7 실측 `0.9 µs/개` × 554개 |
| 잃는 것 | **자석 픽업의 존재 이유** + 이미 번 경험치 | `ExpDrop.cs:51` `PullAllToPlayer` 는 거리 무관 전체 회수 |

얻는 쪽 숫자가 **DEV 자신의 측정**이라는 점이 결정적이었다. 게다가 `PERF.md` §8-8 에서
*"`ExpDrop` 이 주범"* 이라는 귀속을 **이미 철회**해 놨다. 그 문서를 안 읽고 인계문만 봤으면
*"씬이 무거워지는 원인"* 이라는 표현을 그대로 받아 수명을 뒀을 것이다.

### 왜 자석이 죽나

`magnetActivationRange = 8`(`ExpDrop.cs:26`)이고 카메라 ortho 6 이라 **화면 반높이가 6** 이다.
⇒ **세로로 화면 안이면 구슬은 무조건 따라온다.** 쌓이는 건 가로로 흘린 것과 화면 밖뿐이고,
**그 쌓인 더미가 곧 자석의 밥**이다. 수명을 두면 자석의 가치가 "그동안 흘린 양"에서
"최근 N초에 흘린 양"으로 바뀌는데 후자는 거의 0 이다.

## 4. 🔑 물어본 축이 틀렸다 — 진짜 문제는 **누적**이다

`WaveManager.ClearWave`(`:318`)는 **씬 전체를 뒤져 적을 despawn** 하면서 **구슬은 안 건드린다.**
그래서 구슬은 웨이브 하나가 아니라 **한 판 10층 전체**에 걸쳐 쌓인다.
`C27` 계산으로 한 판 처치 수가 **≈551** — 즉 DEV 가 본 **554개는 이론 천장을 이미 본 값**이다.
0.5 ms 는 시작값이 아니라 **최악값**이다.

⚠️ 그리고 554 는 **실제 플레이에 없는 조건**이다. 하네스가 `kiting=true` 로 계속 도망쳤기 때문이다.
**적 800 이 `Waves.csv` 에 없는 것과 같은 이야기** — `PERF.md` §8-4 의 논법 그대로다.

## 5. ✅ 그래서 낸 답 — **새 정책을 만들지 않았다**

`WaveManager.RecycleFarEnemies`(`:246-269`)의 주석이 답을 이미 적어 놨다:

> *"너무 멀어진 적을 **죽이지 않고** 플레이어 주변으로 옮긴다. … **지우면 경험치·골드가 증발하니**
> 옮겨서 다시 쓴다."*

**적에게는 이 원칙이 있고 구슬에는 없다. 그게 전부였다.**

| | |
|---|---|
| 어디에 | `MaintainRoutine`(`:223`) 안, `RecycleFarEnemies()` 옆 — **이미 있는 0.25초 주기를 탄다** |
| 기준 | `SpawnRadius × RecycleRadiusMult` = `20 × 1.9` = **38유닛**. 적과 **같은 상수** |
| 처리 | 즉시 `CollectXp` 합산 1회 + 풀 반환 |

🔴 **`_forcePull`(날아오게)은 안 된다고 못 박았다** — 38유닛을 `magnetSpeed 22` 로 오면 1.7초간
계속 `Update` 를 돈다. **개체 수를 줄이려는 목적에 정면으로 반한다.**

⚠️ 막힐 수 있는 지점도 같이 적었다: 한 번에 레벨이 여러 번 오를 수 있어
`LevelUpManager` 가 큐를 처리해야 한다. **못 하면 내 판단 사항이 아니라 DEV 가 알려 줄 일**이다.

## 6. 이건 밸런스가 **바뀌는** 변경이다 — 추측하지 않았다

지금은 뒤에 흘린 구슬이 **조용히 소실**되고 있으므로, 회수하면 **경험치 수입이 는다.**
얼마나 느는지 **숫자를 만들지 않았다.** 대신 요청 판정 ③ 으로 로그를 요구했다:

```
[WaveManager] 원거리 구슬 회수 N개 · XP +M
```

`M` 이 오면 `TUNING.md` §I-3 에 적는다. 경험치 곡선(`xpThresholds`)은 아직 자리표시 값이고
`TUNING.md` §3 의 순서상 **그게 먼저** 확정돼야 하므로 지금 미리 손대지 않는다.

`BALANCE.md` 는 "수치를 고치는 법"이 담기는 곳이라, 값이 아니라 **못 넘는 선**을 적는 게 맞다.

| 올리려는 값 | 규칙 |

| ~400 | 🟢 그냥 올린다 (비용 차이가 측정 노이즈 안) |
| 400 초과 | 🔴 `REQ/DEV.md` 요청 — `NeighborBufSize`(64) 의 전제가 깨진다 |

도메인 리로드로 세션이 갈리고 세션 간 편차가 ±30 % 라, ms 로 비교하면
**버퍼를 키웠는데 빨라지는** 착시가 난다(`PERF.md` §8-4).

ℹ️ **130 에 성능 근거는 없었다.** `SETUP_STATUS.md:1580` 이 난이도 곡선으로 정했다고 적어 놨고
성능은 이번에 처음 쟀다. ⇒ *"장르답게 더 많이"* 는 이제 **성능이 아니라 체감**의 문제다 → `TUNING.md` §I-1.

## 8. ② 겹침 — 실측값을 **판정 기준으로** 박았다

`TUNING.md` §I-2 에 3상수(`0.85`/`0.9`/`4`)와 각각을 올렸을 때/내렸을 때를 표로 적고,
아래 두 값을 **넘겨야 개선**이라고 못 박았다:

| 지표 | 버퍼 12 | 버퍼 64 (현재) |
|---|---:|---:|
| 평균 최근접 거리 | 0.3144 | 0.3400 (+8.1 %) |
| 0.5유닛 내 이웃 보유 비율 | 84.6 % | **85.1 %** |

🔑 **이 표가 §I-2 의 존재 이유다.** DEV 가 이웃 버퍼를 12→64 로 키웠는데 겹침은 **꿈쩍도 안 했다.**
⇒ 절단은 증상이고 원인은 밀도다. 상수를 만질 사람이 *"고쳤으니 나아졌겠지"* 로 넘어가지 않게
**무엇이 실제로 떨어져야 하는지**를 숫자로 남겼다.

🟡 값으로 안 될 가능성도 같이 적었다 — 적 콜라이더가 트리거라 **물리 반발이 없고 조향으로만** 밀어낸다
(`EnemyBase.cs:203-205`). 그렇다면 상수가 아니라 **DEV 의 설계 결정**이다.

## 10. 남긴 것

- **인계문을 요약으로 읽지 않는다.** 인계문은 구슬 누적을 *"씬이 무거워지는 원인 중 하나"* 라고 불렀는데,
  같은 저자가 `PERF.md` §8-8 에서 **그 귀속을 이미 철회**해 놓았다.
  **넘겨받은 문장보다 넘겨받은 측정치가 정확하다** — 원본을 열어야 보인다
- **"이걸 할까요?"에는 "네/아니오"가 아니라 그 축이 맞는지로 답한다.** 물어본 것은 *수명* 인데
  실제 성장 축은 *`ClearWave` 가 구슬을 안 치운다* 였다. 수명을 뒀으면
  **누적은 그대로 두고 자석만 죽였을 것**이다. `C27`(가격 vs 배수구)과 같은 패턴이 두 번째다
- **답을 만들기 전에 이 프로젝트가 이미 세운 원칙을 먼저 찾는다.** `RecycleFarEnemies` 주석이
  *"지우면 경험치가 증발하니 옮겨서 다시 쓴다"* 라고 **똑같은 문제에 대한 답을 이미 적어 놨다.**
  새 정책을 발명하지 않고 **적용 범위만 넓히면** 되는 일이었다
- **밸런스가 바뀌는 변경이면 숫자를 요구하고 그 자리에서 추측하지 않는다.**
  회수량은 로그 한 줄이면 실측되는데, 그걸 안 받고 "10~30 % 늘 것 같다"고 적으면
  그 숫자가 다음 사람에게는 근거로 읽힌다
