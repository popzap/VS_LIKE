## 1. 요청을 받자마자 막혔다 — 그리고 그건 CONTENT 가 예고한 자리였다

요청-21 §3 에 이렇게 적혀 있었다:

> *"⚠️ 레벨업이 한 번에 여러 번 오를 수 있다. `LevelUpManager` 가 큐를 처리하는지 확인해 줘 —
> 못 하면 이 요청은 거기서 막힌다."*

**확인했다. 큐는 없었다.**

```csharp
// ExperienceManager.cs:145
while (CurrentXp >= XpToNext) { ...; TriggerLevelUp(); }   // 레벨마다 부른다

// LevelUpManager.cs:53 (수정 전)
_currentChoices = PickItems(cards.Length);                 // 직전 후보를 그냥 덮어쓴다
levelUpPanel.SetActive(true);
```

한 번의 `CollectXp` 로 3레벨이 오르면 패널이 3번 다시 만들어지고 **마지막 것만 남는다.**
카드를 하나 고르면 창이 닫히고 끝 — **나머지 2장이 조용히 사라진다.**
얼어붙지는 않는다(`GameManager.ChangeState:117` 의 `CurrentState != LevelUp` 가드가 막아 준다).
**정지가 아니라 조용한 손실**이라 더 안 보였다.

지금은 구슬 하나가 주는 XP 가 작고 **개체마다 따로** `CollectXp` 를 불러서 잘 안 드러난다.
🔴 **그런데 요청-21 은 수백 개를 합산해 한 번만 부르라고 한다** — 옳은 요구지만,
그러면 다중 레벨업이 예외가 아니라 **기본 동작**이 된다.
⇒ [`BUGS.md` `B10`](../BUGS.md) 으로 등재하고 **사용자 판단(2026-09-03)으로 먼저 고쳤다.**

## 2. `B10` 수정 — 빚을 세고 하나씩 갚는다

`LevelUpManager` 에 `_pendingLevelUps` 를 두고, `ShowLevelUpPanel` 은 **떠 있는 패널을 덮지 않는다.**
`HidePanel` 이 하나씩 소진하며 남아 있으면 다시 연다.

🔑 **상호작용 하나를 설계 도중에 잡았다.** 처음 안은 `HidePanel` 에서 무조건 하나 깎는 것이었는데,
**진화 제안 패널(`ShowForcedChoices`)이 떠 있는 동안 레벨업이 들어오면** 진화 카드를 고른 것이
레벨업 빚을 갚은 것으로 세어져 **대기 중인 레벨업이 그대로 사라진다.**
그래서 `_panelIsForced` 로 패널 종류를 구분한다 — **진화는 빚을 만들지도 갚지도 않는다.**

| 경우 | 결과 |
|---|---|
| 3레벨 동시 | 카드 3장 (하나 고를 때마다 다음 장) |
| 진화 제안만 | 카드 1장, 그대로 닫힘 |
| 진화 중 레벨업 1회 | 진화 카드 → **이어서 레벨업 카드** |

`ResetRunState()` 에서 둘 다 초기화한다 — 이월되면 새 런 시작하자마자 패널이 뜬다.

## 3. 요청-21 — 38유닛 밖 구슬을 그 자리에서 거둔다

`WaveManager.RecycleFarExpDrops()` 를 `MaintainRoutine`(0.25초) 안,
`RecycleFarEnemies()` **바로 옆**에 넣었다. 새 코루틴도 새 상수도 없다 —
`RecycleRadiusMult = 1.9` 를 **적과 그대로 공유**한다.

- 🔴 `_forcePull` 은 쓰지 않는다. 38유닛을 `magnetSpeed 22` 로 오면 1.7초가 걸리고
  그동안 계속 `Update` 를 돈다 — **개체 수를 줄이려는 목적에 정면으로 반한다**
- 🔴 합산해서 `CollectXp` 를 **한 번만** 부른다. 수백 개가 각자 부르면 획득음도 그만큼 쌓인다
- `ExpDrop.Harvest()` 는 **XP 를 더하지 않고 양만 돌려준다** — 합산은 부르는 쪽 몫이다

### 씬 전체 순회를 만들지 않았다

`RecycleFarEnemies` 는 `_alive` 목록을 쓰는데 구슬에는 목록이 없었다.
0.25초마다 `FindObjectsByType<ExpDrop>` 을 도는 건 **`D27` 이 방금 걷어낸 바로 그 패턴**이라,
`ExpDrop` 에 `OnEnable`/`OnDisable` 로 유지되는 정적 목록 `ExpDrop.Active` 를 뒀다.
풀 반환도 `SetActive(false)` 라 같은 경로를 탄다(`ObjectPool.Return:61` 확인).

➕ **`PullAllToPlayer()` 도 같은 목록을 쓰게 바꿨다** — 원래 `FindObjectsByType` 이었다.
의미는 동일하다: 목록에 있다는 것이 곧 활성이라는 뜻이다.

## 4. 검증 — 판정 **5/5 PASS** (플레이 모드 실측)

거리 사다리를 놓았다. 플레이어 기준 `5·15·25·35·37·39·45·80` 유닛에 구슬 하나씩.

```
[D29-DROP] 무적 600s · 구슬 8개 배치 · Active=8 · waveActive=True
[WaveManager] 원거리 구슬 회수 3개 · XP +3
[D29-DROP] 남은 구슬 4개 — 거리: 15.0  25.0  35.0  37.0
[D29-DROP] Lv=1 Xp=4 state=Wave waveActive=True
```

| # | 판정 기준 | 결과 |
|---|---|---|
| ① | 웨이브를 넘어 단조 증가하지 않을 것 | ✅ 조작 없이 **8 → 4개** |
| ② | 회수된 경험치가 버려지지 않을 것 | ✅ `CurrentXp 4` = 회수 3 + 자동흡수 1 |
| ③ | 회수량 로그 | ✅ `원거리 구슬 회수 3개 · XP +3` |
| ④ | 자석이 죽지 않을 것 | ✅ 38 **안**은 그대로 남았다 |
| ⑤ | 콘솔 에러·경고 | ✅ **0** |

🔑 **임계값이 정확히 38 이라는 것이 사다리로 증명됐다** — 걷힌 것 `39·45·80`,
남은 것 `15·25·35·37`. 경계가 37 과 39 사이다. `SpawnRadius 20 × 1.9 = 38` 그대로다.

> ⚠️ **경계 양쪽에 하나씩 놓지 않았으면 "38"은 주장에 그쳤다.** `D25` 의 교훈 180
> (*경계가 0 인 판정은 아무것도 증명하지 못한다*)을 이번엔 설계에 먼저 넣었다.

**B10 검증** (같은 세션, 별도 시행):

```
[B10] before  Lv=1 state=Wave
[B10] CollectXp(40) 후  Lv=4 state=LevelUp timeScale=0
[B10] HidePanel 1회  state=LevelUp
[B10] HidePanel 2회  state=LevelUp
[B10] HidePanel 3회  state=Wave timeScale=1
```

3레벨이 올랐고 **`HidePanel` 을 세 번 다 써야** `Wave` 로 돌아온다.
수정 전이라면 **1회에 끝났을 것**이다 — 그게 곧 카드 2장 유실이다.

🔴 **`SampleScene.unity` 는 한 줄도 안 바뀌었다.** 검증은 전부 `RunCommand` 로 했고
임시 MonoBehaviour·씬 오브젝트를 만들지 않았다 (`git status` 로 확인).

## 5. ⚠️ 밸런스가 바뀌었다 — 숫자는 CONTENT 몫

지금까지 뒤에 흘린 구슬은 **조용히 소실**되고 있었다. 이제 회수되므로 **경험치 수입이 는다.**
얼마나 느는지는 **추측하지 않는다** — ③ 로그의 `XP +M` 을 실플레이에서 보고 정한다.
`ExperienceManager.xpThresholds` 는 자리표시 값이라 **지금 미리 손대지 않았다.**
