# D18 — 무기 장부를 하나로 합쳤다 (B6)

**세션:** DEV · **날짜:** 2026-08-31 · **버그:** [`BUGS.md` B6](../BUGS.md)
**방향 결정:** 사용자 (2026-08-31) — 제시한 A·B·C 중 **A안**

---

## 왜 했나

무기 개수를 세는 장부가 **둘**인데 서로 안 맞았다.

| 세는 쪽 | 무엇을 세나 |
|---|---|
| `LevelUpManager.CanAcquire` | `_inventory` 의 Weapon 항목 수 |
| `WeaponManager.AddOrUpgradeWeapon` | `_weapons` 딕셔너리 크기 |

`GameManager.cs:228` 이 시작 무기를 **`WeaponManager` 에 직접** 넣어서
`_inventory` 를 건너뛰었다. 그래서 매 판 시작부터
`_weapons.Count == CountOwned(Weapon) + 1` 이 성립한다.

### 🔴 증상이 넷이다 — 개수만이 아니었다

원인이 하나라 같이 닫힌다. 세 개는 B6 등재 당시에는 안 적혀 있었다.

| # | 증상 | 왜 |
|---|---|---|
| ① | 무기 칸이 **하나 모자란다** | `CanAcquire` 가 통과시킨 걸 `AddOrUpgradeWeapon` 이 거절 → `무기 슬롯 꽉 참` 경고 |
| ② | 시작 무기가 레벨업 카드에 **"신규"로 다시 뜬다** | `_inventory` 에 없으니 미보유 취급. 고르면 슬롯을 한 칸 더 먹으면서 무기는 안 는다 |
| ③ | `HasItem`·`GetItemLevel` 이 **거짓말한다** | 시작 무기에 대해 `false` / `0` |
| ④ | **진화 재료 판정에서 빠진다** | ③ 때문에 시작 무기를 재료로 쓰는 레시피가 성립하지 않는다 |

## 무엇을 했나 — A안 (장부를 하나로)

| 경로 | 무엇 |
|---|---|
| `Assets/Scripts/LevelUp/LevelUpManager.cs` | `GrantStartingWeapon(WeaponData, int)` + `FindWeaponItem(WeaponData)` 신설 |
| `Assets/Scripts/Core/GameManager.cs` | `ApplySelectedClass()` 가 `WeaponManager` 대신 이쪽을 부른다 + 경고 주석 |

```cs
// 전 — WeaponManager 직행. _inventory 를 건너뛴다
WeaponManager.Instance?.AddOrUpgradeWeapon(cls.StartingWeapon, lv);
// 후 — 장부에 등록하면서 지급
LevelUpManager.GrantStartingWeapon(cls.StartingWeapon, lv);
```

### 왜 `ApplyItem` 을 재활용하지 않았나

`ApplyItem` 은 **"한 레벨 올린다"** 라서 `_inventory[item]++` 를 한다.
`StartingWeaponLevel` 이 2 이상인 직업이 생기면 맞지 않는다.
`GrantStartingWeapon` 은 레벨을 **그대로 박는다**.

### 대응 `ItemData` 가 없으면

`allItems` 에서 `WeaponRef` 로 역조회한다. 못 찾으면 **무기는 주되 경고를 남긴다** —
조용히 넘어가면 B6 이 그대로 되살아난 채 아무도 모른다.

지금은 셋 다 있다:

| 직업 | 시작 무기 | 대응 `ItemData` |
|---|---|---|
| Warrior | Sword | ✅ `Sword.asset` |
| Ranger | Bow | ✅ `Bow.asset` |
| Mage | Fireball | ✅ `Fireball.asset` |
| Aegis · Doomlord · Sentinel (승급) | 없음 | — (`StartingWeapon` 이 null) |

### ⚠️ 호출 순서에 묶여 있다

`GameManager.StartRun()` 이 `ResetRunState()` → `ApplySelectedClass()` 순으로 부른다.
**뒤집으면 `_inventory.Clear()` 가 시작 무기를 지운다.** 주석에 박아 뒀다.

## 어떻게 확인했나

실플레이(Warrior)로 두 단계.

### ① 런 시작 직후 — 장부 대조

```
CountOwned(Weapon) = 1
_weapons           = 1
차이(0 이어야)     = 0        <- 예전엔 1
무기 슬롯 상한     = 3
장부: Sword Lv1 HasItem=True
실제 무기: Sword
```

### ② 상한까지 채우기 — 예전엔 3번째가 거절당했다

```
Sword HasItem=True GetItemLevel=1   <- 증상 ②③ 닫힘
Bow  CanAcquire=True → 무기 1→2  OK
Gun  CanAcquire=True → 무기 2→3  OK
CountOwned=3  _weapons=3  상한=3
꽉 찬 뒤에도 CanAcquire=true 인 신규 무기 = 0
```

### 판정

| # | 확인할 것 | 결과 |
|---|---|---|
| ① | 두 장부의 수가 같다 | ✅ 차이 0 (예전 1) |
| ② | 상한까지 실제로 채워진다 | ✅ 3/3, 거절 0 |
| ③ | 🔴 `무기 슬롯 꽉 참` 경고가 안 뜬다 | ✅ 콘솔 6건 전부 `Log` — 경고 0 |
| ④ | 시작 무기가 보유로 잡힌다 | ✅ `HasItem=True` · `GetItemLevel=1` |
| ⑤ | 꽉 찬 뒤 신규가 후보에서 빠진다 | ✅ 0건 (과잉 제안 없음) |
| ⑥ | 컴파일 에러 0 | ✅ |

**정리 확인** — 임시 스크립트·오브젝트 없음(전부 `RunCommand` 일회성) · 플레이 종료 · 콘솔 0.

## 알게 된 것

### 장부가 둘이면 증상은 넷으로 갈라진다

B6 은 "무기 칸이 하나 모자란다"로만 등재돼 있었다. 실제로는 **카드 재출현 · 조회 거짓말 ·
진화 재료 누락**이 같은 뿌리에서 나온다. 개수만 맞추는 B안을 골랐다면 나머지 셋이 남았다.

### 이런 종류는 "차이를 세는" 것으로 잡힌다

두 장부의 값을 각각 로그로 찍는 게 아니라 **뺄셈 한 줄**을 찍었다.
0 이 아니면 그 자체가 버그다 — 다음에 어긋나도 같은 프로브로 바로 드러난다.
