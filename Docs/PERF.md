## 0. 왜 재나

뱀서라이크는 화면에 적이 수백 마리 뜨는 것이 장르의 정의다.
이 프로젝트도 웨이브 상한이 `MaxAlive = 100`(`Assets/Scripts/Wave/WaveData.cs:56`)이고,
그 위에 엘리트·보스는 **상한을 무시하고** 더 얹는다(`WaveManager.cs:193`).

그런데 이 프로젝트는 **성능을 한 번도 재 본 적이 없다.**
`ROADMAP.md` §6 에 "`OverlapCircleAll` 이 할당한다" 같은 *코드를 읽고 쓴 추측*은 있지만
숫자가 없다. 추측만으로 고치면 **엉뚱한 데를 고치고 고쳤다고 믿게 된다** —
실제로 D27 조사 1단계에서 1순위 가설이 이미 한 번 무너졌다(§6-A).

#### 🔴 함정 ① — **품질 레벨을 올리면 vSync 가 같이 켜진다**

`vSyncCount` 는 프로젝트 전역이 아니라 **품질 레벨마다 따로 저장된다.**
Very Low 에서는 `0` 이었는데 Ultra 로 올리자 `1` 이 됐다.

파일럿 측정에서 그대로 드러났다 — **`p50 = 6.804 ms`**, 즉 정확히 **144 Hz(6.94 ms)** 다.
프레임 타임이 모니터 주사율에 붙어 있어 **적을 400마리 세워도 숫자가 안 움직인다.**

> 이 문서 §1-3 에 *"vSync 가 켜져 있으면 병목이 안 보인다"* 고 적어 두고 **바로 그 함정을 밟았다.**
> 원인은 "vSync 를 확인했다"가 아니라 **"확인한 시점과 측정한 시점의 설정이 달랐다"** 는 것이다.
> ⇒ **환경값은 측정 시작 시점에 하네스가 직접 읽어 로그로 남긴다.** 사람이 미리 확인한 값은 못 믿는다.
> (`PerfHarness.Prepare()` 가 매 실행마다 vSync 를 끄고, `LogEnvironment()` 가 실제값을 찍는다)

#### 🔴 정정 ② — **"Game 뷰가 640×480 이다"는 틀렸다**

편집 모드에서 `Screen.width/height` 를 읽고 640×480 이라고 판단했지만,
**플레이 모드에서 실제로 찍힌 값은 `1920×1080` 이었다.** 편집 모드의 `Screen` 은
게임 뷰의 실제 렌더 타겟이 아니다. 해상도는 손댈 필요가 없었다.

> ⇒ **재는 값은 재는 상태에서 읽어야 한다.** 위 함정 ①과 같은 뿌리의 실수다.

#### 🔴 함정 ③ — **`Assets/Refresh` 는 재컴파일을 보장하지 않는다**

계측 코드를 넣고 `Assets/Refresh` → `IsCompiling=false` → **콘솔 에러 0** 을 확인했는데,
로드된 `Assembly-CSharp` 을 뒤져 보니 **새 필드가 하나도 없었다.** 컴파일 자체가 안 돈 것이다.

`CLAUDE.md` §4 의 "Refresh → sleep → 콘솔 확인" 절차는 **에러가 없다는 것만 확인할 뿐
반영됐다는 것을 확인하지 못한다.** 이걸 모르면 "고쳤는데 안 먹네"를 엉뚱한 데서 찾게 된다.

**대응:** `UnityEditor.Compilation.CompilationPipeline.RequestScriptCompilation()` 을 직접 부르고,
반영 여부는 **로드된 어셈블리에서 새 심볼을 조회해** 확인한다.

### 1-4. 🔴 이 측정의 한계 — 반드시 같이 읽을 것

**에디터 플레이 모드에서 잰다. 빌드가 아니다.** 그래서:

- 절대값(ms)은 **빌드보다 나쁘게 나온다.** 에디터는 인스펙터 갱신·씬 뷰·프로파일러 수집을
  같은 프로세스에서 돌린다. **"우리 게임은 N ms 다"라고 말하면 안 된다.**
- 이 문서가 주장하는 것은 **같은 조건에서의 상대 비교(before/after)** 뿐이다.
  에디터 오버헤드는 양쪽에 똑같이 얹히므로 **차이는 유효하다.**
- 에디터는 **포커스를 잃으면 프레임을 진행하지 않는다.** 측정 중 창을 내리면 표본이 오염된다.

> ℹ️ 빌드 측정을 하려면 웨이브까지 자동으로 진입하는 경로가 필요하다. 마감(2026-09-07) 안에
> 넣을 수 있으면 넣고, 못 넣으면 **위 한계를 문서에 남긴 채로** 상대 비교만 주장한다.

### 🔴 평균은 적지 않는다

뱀서라이크에서 사람이 "렉"이라고 부르는 것은 **평균이 아니라 스파이크**다.
60 fps 평균에 100 ms 스파이크가 초당 한 번 있으면 플레이어는 "느리다"가 아니라 **"끊긴다"**고 느낀다.
그래서 프레임 타임은 항상 이렇게 적는다:

**`p50 / p95 / p99 / max`** (단위 ms)

평균(mean)은 참고로만 적고, **판정에는 쓰지 않는다.**

## 4. 시나리오

적 수는 **200 / 400 / 800** 세 구간. 웨이브 상한 100 을 **일부러 넘긴다** —
상한 안에서만 재면 "상한이 성능 때문에 100 인지, 밸런스 때문에 100 인지"를 구분할 수 없다.

| # | 이름 | 무엇이 도는가 | 무엇을 분리하나 |
|---|---|---|---|
| **A** | 적만 | 적 이동 + 무리 분리 + 렌더 | 무기·투사체를 뺀 **순수 적 처리 비용** |
| **B** | 적 + 무기 | A + 플레이어 무기 전부 발사 | 할당 8곳(§6-B)이 실제로 얹는 비용 |

**A 를 먼저 잰다.** B 만 재면 어느 쪽이 원인인지 못 가른다.

### 부하 하네스 요구사항

- 웨이브 상한(`MaxAlive`)과 무관하게 **N 마리를 세우고 그 수를 유지**한다
- 소환 위치 분포는 실제 게임과 같아야 한다 (`WaveManager.GetSpawnPosition` 과 같은 링)
- 시나리오 A 에서는 적이 죽지 않아야 한다 — 표본 구간 중 N 이 변하면 조건이 흔들린다
- 🔴 **측정이 끝나면 하네스는 씬과 저장소에서 지운다** (`CLAUDE.md` §4)

## 7-G. 프레임 구간 분해 (2026-09-02)

### 방법 ① 프로파일러 샘플러 — **절반만 된다**

Gfx.WaitForPresentOnGfxThread=0.000
EditorLoop=0.000
Camera.Render=0.004      ← URP 는 이 샘플러를 안 쓴다

| v5, 렌더러 OFF | **11.29 ms** |

**렌더러를 껐는데 3 ms 느려졌다.** 렌더 비용이 음수일 수는 없다.
원인은 그 사이에 하네스가 v1 → v5 로 바뀐 것이다 — `Recorder` **10개를 매 프레임 읽고**,
그 `enabled = true` 자체가 엔진에 계측 오버헤드를 얹는다.

> §1 에 *"하나라도 다르면 비교가 무효"* 라고 써 놓고 그걸 **환경 설정에만 적용하고
> 계측 코드에는 적용하지 않았다.** ⇒ **계측 코드 버전도 환경의 일부다.**
> `PerfHarness.Version` 상수를 만들어 매 측정 전에 확인하도록 했다.

### 최종 분해 — 적 800 · 시나리오 A · 렌더러 ON

| 구간 | ms/frame | 비중 |
|---|---:|---:|
| **프레임 전체 (p50)** | **13.035** | **100 %** |
| `PlayerLoop` | 8.118 | 62 % |
| ↳ `FixedBehaviourUpdate` | 3.370 | 26 % |
| ↳↳ 🔴 **무리 분리 (질의 + 누산)** | **2.451** | **19 %** |
| ↳ `LateBehaviourUpdate` (`EnemyVisual`) | 1.115 | 9 % |
| ↳ `Physics2D.Simulate` | 0.524 | 4 % |
| ↳ `BehaviourUpdate` | 0.245 | 2 % |
| ↳ 나머지 (렌더 제출 등) | ≈ 2.9 | 22 % |
| **`PlayerLoop` 바깥** (에디터 루프·프레젠트) | **4.917** | **38 %** |
| *(참고) 적 렌더 — 대조군으로 분리* | *1.74* | *13 %* |

### 이 표에서 읽어야 할 것

1. 🔑 **무리 분리가 스크립트 비용 중 가장 크다 (19 %).** 적 렌더(13 %)보다도 크다.
2. **`Physics2D.Simulate` 는 4 % 밖에 안 된다.** Rigidbody2D 800개가 문제가 아니다 —
   문제는 **우리가 직접 부르는 질의**다. ⇒ 물리 설정을 손대는 방향은 의미 없다.
3. **38 %가 `PlayerLoop` 바깥이다.** 에디터 자체 비용이고 **빌드에는 거의 없다.**
   즉 빌드에서는 나머지 구간의 비중이 지금보다 **커진다** — 분리 질의의 상대 비중도 올라간다.
4. ❌ **`GC.Collect = 0.000`.** 프레임당 17~39 KB 를 할당하지만 **정지를 만들고 있지 않다.**
   "할당이 크니 GC 가 스파이크의 범인"이라는 가설은 **틀렸다.**

### 이 측정에서 밟은 함정 7가지 (전부 실제로 겪은 것)

| # | 함정 | 어떻게 드러났나 |
|---|---|---|
| ① | 품질 레벨을 올리면 **vSync 가 따라 켜진다** | `p50 = 6.804 ms` = 정확히 144 Hz |
| ② | 편집 모드 `Screen` 은 **실제 렌더 타겟이 아니다** | 640×480 인 줄 알았는데 플레이 모드는 1920×1080 |
| ③ | `Assets/Refresh` 는 **재컴파일을 보장하지 않는다** | 에러 0 인데 새 필드가 어셈블리에 없었다 |
| ④ | **레벨업이 게임을 멈춘다** | 적 200이 살아 있는데 분리 질의 **0회** |
| ⑤ | **웨이브 제한시간 만료** | 표본 전체가 걸러져 **0으로 가득 찬 행** |
| ⑥ | **`0.000 ms` 는 "비용 없음"이 아니다** | URP 는 `Camera.Render` 를 안 쓴다 — 측정을 안 한 것 |
| ⑦ | **계측기를 바꿔 놓고 비교했다** | 렌더러를 껐는데 3 ms 느려졌다 |

🔑 **①·②·⑦은 뿌리가 같다 — "재는 값을 재는 상태에서 읽지 않았다."**
그래서 하네스가 매 실행마다 환경값을 직접 읽어 로그로 남기고,
`PerfHarness.Version` 으로 **코드 반영 여부까지** 확인하게 만들었다.

🔑 **④·⑤는 더 위험한 종류다 — 에러도 경고도 없이 표가 그럴듯하게 채워진다.**
"적 200마리인데 질의 0회"라는 **물리적으로 불가능한 값**이 없었으면 못 잡았다.
⇒ 측정에는 **불가능한 값을 드러내는 지표**를 반드시 하나 끼워 넣는다.
